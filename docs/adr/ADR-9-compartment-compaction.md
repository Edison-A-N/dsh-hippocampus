# ADR-9: Compartment compaction — magic-context's historian on the CompactionEngine seam

## Status

Accepted (2026-11-05). Supersedes ADR-7 as the default engine; reverses the compartment part of ADR-8. ADR-7's engine stays as the inline fallback and as `HIPPOCAMPUS_COMPACTION=checkpoint`.

## Context

The single-checkpoint engine (ADR-7) waits until 65% pressure, prepares one summary, and commits it at 80%. In practice long sessions sat in the 65–80% band for hours; on a route that reports no prompt-cache use, every one of those steps was billed at full price for a near-full window. magic-context, which summarizes continuously in the background, keeps comparable sessions far lower.

Reading magic-context 0.49.12 showed the difference is not the thresholds — its execute threshold is also 65% — but three mechanisms ADR-8 had deferred:

1. The historian fires on the size of the unsummarized tail (3 × triggerBudget, triggerBudget = 5% of usable context clamped to 5K–50K), not on pressure.
2. Summaries are compartments with four tiers, rendered with a decay curve inside a 15% history budget.
3. Commits ride moments the provider cache is already dead (idle past the TTL, model change, system-prompt change); pressure is only the backstop.

## Decision

Implement those three on the existing seam, without a message-transform hook (ADR-3 still holds):

- **Trigger.** `compactIfNeeded` measures the eligible span (surface after the current checkpoint and pending compartments, before the protected tail). It starts one background historian call when the span ≥ 3 × triggerBudget, or ≥ 1 × triggerBudget once pressure ≥ threshold − 2%, or at the force band (max(85%, threshold + 2%)). Protected tail = magic-context's formula: 30% × usable × (1 − pressure), clamped to [min(12K, 8% usable), min(96K, 40% usable)], never splitting a tool arc.
- **Historian call.** One `ctx.llm.stream` call over one chunk (≤ 25% of the historian model's window, clamped to 8K–50K formatted tokens). The transcript is compact: `U:` user text (long text keeps head and tail, 6,000 chars), `A:` agent text (same cap), `TC:` tool calls with clipped args, `TR` tool-result heads, `AGENT REPORT` for sub-agent messages, harness-injected context (skill catalog, time and runtime context) skipped or labelled `CONTEXT(kind)`, reasoning dropped. Output is JSON compartments (start/end seq, title, importance, p1–p4), parsed and snapped onto the slice; when the last compartment ends early, the slice is cut back to the last tool-balanced point inside it and the rest waits for the next run. The slice must still be on the surface when the call returns, else the result is discarded. Rows land in SQLite as `pending`; the surface is untouched.
- **Commit.** When pending compartments exist and (pressure ≥ threshold, or the route reported no cache reads/writes in ≥ 3 samples, or no model response for longer than the cache TTL), one replace covers [previous checkpoint or first non-system node … last pending end] with a new checkpoint. The checkpoint renders every compartment through the decay curve (H = 24·2^((imp−50)/25)/p, tier cuts 0.201/0.729/1.322/2.587, p = natural cost / budget) plus an oldest-first downgrade loop with the real token estimator. Headings carry `§start–end§` seq ranges and the checkpoint names the session id, so `ctx_expand` reaches the raw events.
- **Lineage.** The store remembers the checkpoint's seq. Every pass checks that it is still the node right after the system head and that pending rows tile the surface from there; any mismatch (fork, foreign replace, pruned node) drops the affected rows and their span is summarized again from the raw events.
- **Blocking paths.** Overflow, ≥ 95% with nothing pending, and `/compact` wait for a running historian, then run up to 6 chunks inline and commit. If no compartment could be produced, ADR-7's single-checkpoint summary runs instead.
- **Failures** back off 30s, doubling to 15 min, per session.

## Rejected alternatives

- **Only lower ADR-7's thresholds.** Each fold re-summarizes the previous summary plus everything since; at depth 3+ fidelity degrades (ADR-8), and every fold busts the cache.
- **Render the decay into m[0]/m[1] per request** (magic-context's exact shape). Needs the per-request transform hook DSH does not have (ADR-3).
- **Keep pending summaries in memory only** (ADR-7). A restart loses the work; SQLite rows survive and are cheap.

## Consequences

- Replaying a long real session log through the new engine (fake historian, same token heuristic) keeps pressure well below the 65% band the old engine sat in, at the cost of a handful of small historian calls.
- More, smaller model calls in the background; each reads a chunk, not the whole prefix. A cheap historian model (`HIPPOCAMPUS_HISTORIAN_PROVIDER/_MODEL`) cuts cost further; unset, the session's model is used.
- On cached routes the extra busts land on cold-cache moments; a warm session below 65% never pays for a commit.
- Still deferred from ADR-8: historian fact capture into memories, smart notes, and magic-context's reasoning drop and `ctx_reduce` passes. Tool-output age and dedup reclaim landed in ADR-10, which also wired the model-change commit trigger listed above; system-prompt changes are still not a trigger (not visible at pre-step). The idle commit's 5-minute TTL is shorter than some routes' caches (ADR-10).
- **Coexistence with the preset's stock backend.** The Web profile mounts `compaction-basic` (80% threshold) and `tool-result-pruner` inside every agent preset's isolated `compaction` group; the profile's host-level `compaction-basic` row is disabled, but the preset copy is not. In practice the preset copy wrote the observed commits. This engine runs on the host `agent/pre-step` / `agent/request-error` events next to it: keeping pressure below 65% means the stock backend rarely fires, and it stays as the 80% safety net. The tool-result pruner lives only in that preset scope and is not reachable from here, so this engine does not prune tool results. A commit is skipped while another compaction transaction is open (an unmatched `compaction/start`). On provider overflow both engines' handlers run; the second sees the surface already replaced. Each keeps its own retry budget: this plugin's handler retries once per agent until the model answers again (the stock backend's `maxOverflowRetries` default).
- Numbers not configurable today: emergency fold at 95%, at most 6 historian chunks per blocking fold, historian output cap 16K tokens, 10-minute historian timeout, 2-minute wait for a running historian before a blocking fold. The decay pressure uses the real rendered cost of each tier instead of magic-context's fixed TIER_COST table.

## Amendment (2026-11-12): one token unit, input capacity, sub-agent task prompt

A long session on a route that reports no cache use compacted first at about half of a 1M window and kept about a third after it. Replaying it showed three porting errors, none of them a cache trade-off:

- **Units.** Pressure came from `measurement.totalTokens`, which the token meter anchors on provider usage, but node prices (protected tail, eligible span, stale distance, history budget) were the meter's chars/4 heuristic. On that route provider tokens ran 1.7–2.4× the heuristic (Chinese and JSON-heavy tool output), so every size threshold was in effect doubled: the 96K tail and the 3 × 32.5K trigger each held about twice their nominal size in provider tokens. magic-context calibrates its estimates per model. Node prices are now scaled by `providerScale`, read at the usage anchor: `baseline.tokens` ÷ the anchor's heuristic price (tool schemas + surface − `surfaceDeltaTokens`), clamped to [0.5, 4], 1 when the meter has no usage anchor. Reading it at the anchor matters: `totalTokens` is usage plus a heuristic delta, so `totalTokens ÷ current surface` jumps after every replace (by about half in the replayed session) and drifts during a step. Only the heuristic part of a node is scaled (`providerPrice`); route-priced image tokens are kept as they are. Shadow prices in `compaction/prune` and `compaction/summary` stay heuristic, because the meter subtracts them in its own unit. The reclaim floor (250 tokens, "a placeholder is worth it") stays heuristic too: it is about the placeholder's size, not context pressure, and scaled it would replace ~120-token results by larger placeholders. The single-checkpoint engine uses the same scale for its retained tail, and the historian chunk budget (a share of the historian's window) is filled in provider tokens too. When the meter has no usage baseline for a step (header changed, or usage below its estimate), the factor is 1 for that step; the meter only reports a usage baseline when usage ≥ its own estimate, so routes below 1× always get 1.
- **Input capacity.** Pressure and every threshold were taken against the raw window. Both engines now use window − min(maxTokens, 25% of the window), magic-context's context limit; the stock backend subtracts maxTokens too. A request header without maxTokens reserves nothing.
- **Sub-agent task prompt.** magic-context runs no historian for sub-agents and never compacts past the live user prompt. This engine did both, and a few delegated sub-agents in the replayed logs lost their task prompt to a checkpoint paraphrase mid-task. A session whose header says `origin: subagent` now keeps its first genuine user message (source kind `user` or none) next to the system prompt (`surfaceHeadEnd`), together with any harness notices before it (a working-directory change sometimes precedes the task prompt); compaction starts after it. Sub-agents still run the historian: long ones grow past a third of a 1M window. Not covered: a forked sub-agent (`isSeeded`), whose surface starts with the inherited parent history and whose own task prompt sits after it; pinning that message would break the contiguous lineage above, so a fork keeps the old behaviour. On upgrade, a sub-agent's pending compartments that started at its task prompt no longer tile from the head and are dropped and summarized again (one extra historian call); a task prompt already inside a checkpoint stays summarized.
- Deliberate and kept: the tail-size trigger counts raw eligible tokens, tool output included, where magic-context counts only the narrative (`U:`/`A:`/`TC:` lines). On tool-heavy sessions magic-context's trigger never fires before the 63% proactive band; counting tool output summarizes them earlier.
- Replay of the session (independent script; k fixed per session from usage before the first replace, raw 1M window, no sub-agent pinning, reclaim floor unscaled, so it checks the calibrated rules rather than this code): summed input fell by about 40% and the peak by about a third; ADR-10's 5-minute idle reclaim lowered the peak a little further.
